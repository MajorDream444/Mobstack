# MobStack Architecture v1.0

**Status:** PROPOSAL

## Authority model

MAIM human doctrine → HAMAL operating doctrine → MobStack execution rails → Industry OS field implementation.

Industry evidence returns upward only as sourced, reviewed proposals.

## Repository contracts

| Layer | Owns | Does not own |
|---|---|---|
| Major-AI-OS | MAIM education, founder mindset, communication and brand doctrine | Industry facts or runtime state |
| HAMAL_MOB_PLAYBOOKS | Context, playbooks, SOPs, rubrics, MOBS and industry patterns | Live application records |
| MobStack | Schemas, routing, adapters, gates, handoffs, receipts and test harnesses | Industry claims or universal doctrine |
| Industry OS | Evidence, decisions, counterparties, pilots, registries and application code | Cross-industry doctrine |

## Runtime contract

A MobStack run requires:

1. a pinned doctrine reference;
2. a pinned playbook reference;
3. a workload repository and commit;
4. an assigned MOB and accountable human;
5. declared permissions and prohibited actions;
6. structured input and expected artifact contract;
7. required gates;
8. a receipt destination.

A host adapter may translate this contract into native instructions. It may not weaken it.

## Learning contract

Industry evidence can generate an upstream candidate. It cannot directly edit HAMAL doctrine. A candidate carries its source workload, evidence class, observed period, scope, and human reviewer.
