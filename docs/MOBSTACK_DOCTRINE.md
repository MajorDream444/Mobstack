# MobStack Doctrine

MobStack is the execution harness for the HAMAL / AMA / Art Mob agent operating system.

It is inspired by G-Stack style startup pressure-testing, but it is not a clone. MobStack exists to turn ideas, repos, tools, prompts, audits, and playbooks into executable AI operating patterns across the 12 MOBS and eventual 144-agent network.

## Core Thesis

The system is not a collection of isolated agents. It is a living operating layer where every agent can:

- identify its Mob and role
- access approved doctrine
- load the right tools
- understand memory boundaries
- produce standardized outputs
- hand work to another agent
- log what changed
- preserve context for the wider network

The goal is simple: no brilliant idea should remain trapped in one chat, one repo, one agent, or one folder.

## Division of Responsibility

### HAMAL_MOB_PLAYBOOKS

HAMAL is the doctrine brain.

It owns:

- system philosophy
- playbooks
- SOPs
- templates
- rubrics
- Mob operating models
- agent context rules
- repo/tool/MCP audits
- industry-specific playbooks

### MobStack

MobStack is the runtime skeleton.

It owns:

- agent schemas
- repo ingestion flows
- install/export patterns
- orchestration patterns
- sub-agent spawning standards
- event and memory sync protocols
- implementation scaffolds
- test harnesses

In plain language: HAMAL tells the agents how we move. MobStack gives them the rails to move consistently.

## Operating Principle

Every new repo, tool, agent, workflow, or random inspiration must be processed through the same question set:

1. What problem does this solve?
2. Which Mob owns it?
3. Which playbook does it strengthen?
4. What memory should be created?
5. What output does it produce?
6. What quality rubric judges it?
7. What should other agents know about it?
8. What should never happen with it?

If it cannot answer these questions, it is not yet part of the operating system.

## The 144-Agent Rule

Do not start by trying to build 144 agents.

Start by making 12 executable MOBS.

Each Mob should first have:

- one lead orchestrator
- three to five working agents
- clear inputs and outputs
- approved tools
- memory rules
- KPIs
- handoff rules
- one showcase workflow

Once the 12 MOBS are executable, the 144-agent network becomes expansion, not chaos.

## The One-Keystroke Memory Goal

When one repo, file, or agent learns something important, the network should know.

This means each meaningful change must generate:

- a commit
- a changelog note
- a memory update
- a Mob assignment
- a suggested next action
- a link back to source material

MobStack should eventually support hooks or scripts that create this automatically.
